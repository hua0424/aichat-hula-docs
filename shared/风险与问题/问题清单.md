## Open
- [ ] **ISS-004** `P2` `ContactMapper.refreshOrCreateActiveTime` SQL 无条件覆盖 `last_msg_id`，Consumer 消费延迟时旧 msgId 可覆盖新 msgId
  - 发现：ISS-003 review 阶段 reviewer E3，manager 2026-05-12 18:55 指示登记
  - 根因：`refreshOrCreateActiveTime` 的 ON DUPLICATE KEY UPDATE 用 `last_msg_id = VALUES(last_msg_id)`，无序保护；与 ISS-003 同事务写入产生竞态
  - 影响：并发或 Consumer 消费延迟时 `last_msg_id` 可能短暂回退，/chat/msg/page 漏返（自愈窗口短）
  - 修复方案：改为 `last_msg_id = IF(VALUES(last_msg_id) > last_msg_id, VALUES(last_msg_id), last_msg_id)`，与 `refreshOrCreateActive` 保持一致
  - 处置：ISS-003 合并后由 server-dev 提单独 PR
  - Owner：server-dev
- [ ] **ISS-005** `P2` `Room.last_msg_id` 在 `skipPush=true`（stream_end）路径下不更新，最近会话列表显示错误
  - 发现：server-dev 2026-05-12 18:28 端到端复测时观察；ISS-003 方案 §2.3 已记
  - 根因：stream_end 写库走 `sendMsg` 但 `skipPush=true`，不发 `MessageSendEvent` → `MsgSendConsumer` 不触发 → `RoomDao.refreshActiveTime` 不调用
  - 影响：最近会话列表显示 owner 最后一条而不是 AI 回复
  - 处置：ISS-003 PR 中已在 `sendMsg` 加 `TODO(ISS-00X)` 注释占位；后续单独 PR 修复（StreamProcessor 持久化后补一次 Room.last_msg_id 推进，或在 sendMsg 内无条件补）
  - Owner：server-dev / plugin-dev 协商
- [ ] **ISS-006** `P2` 发送者 `im_contact.active_time` 永不在 send 路径推进（最近会话列表不冒泡）
  - 发现：backend-tester 2026-05-12 ISS-003 E2E-1 复测时观察到 Dawn(sender) `active_time=2026-05-11` 旧值未变；server-dev task #14 调查锁定根因
  - 根因：`MsgSendConsumer` 仅推进 `Room.active_time` 并发 WS push,**不调用** `contactDao.refreshOrCreateActiveTime`；唯一调用者 `AckConsumer` 用 `Arrays.asList(dto.getUid())` 只推进 ACK 发起方,而 group 房 sender 因 `getMemberExceptUidList` 排除不会收到自己消息的 push,因此也永不 ACK 自己的消息 → sender `im_contact.active_time` 在 send 路径上始终是「上次自己作为 receiver 收到的消息时间」
  - 影响：sender 发完消息后,自己的最近会话列表不会把这个房间冒泡到顶部(列表按 `Contact::getActiveTime` 排序,见 `ContactDao.getContactPage`);客户端如果做服务端权威 contact 列表渲染,会出现「我刚发完一条消息,这个会话却还在列表中间」的 UX bug
  - 复现：room=140789095693824 group,Dawn(uid=10937855681024) send → DB 验证 Dawn 的 `im_contact.active_time` 不变,仅安洁(receiver 且 ACK)的 active_time 推进
  - 修复方案 A(推荐,最小改动):`ChatServiceImpl.sendMsg` 在 `syncContactLastMsgId` 之后调用 `contactDao.refreshOrCreateActiveTime(roomId, memberUidList, msgId, sendTime)` —— ISS-004 已落地的 IF 单调保护可防止与 AckConsumer 异步路径竞态时回退。可只传 sender uid (`[uid]`) 把 AckConsumer 权威性留给 receivers,也可全量(已被 ISS-004 保护)
  - 修复方案 B:在 `MsgSendConsumer.onMessage` 增补 `contactDao.refreshOrCreateActiveTime(roomId, [senderUid], msgId, sendTime)` —— 走 MQ 异步,但 skipPush=true 路径绕过 → 与 ISS-005 同源风险
  - 副发现:`RetryPushConsumer.java:52` 用 `Arrays.asList(Long.parseLong(user.get("uid").toString()))`(`fromUser.uid` 即 sender)调 `refreshOrCreateActive`,但 retry 语义对应的是 receiver 未 ACK,memberUidList 取 sender 看起来像旧 bug —— 与 ISS-006 同一文件域,可在同 PR 校正或单独跟进
  - Owner：server-dev

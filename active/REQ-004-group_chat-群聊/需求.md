## 一、概述

### 一句话
让 aiclaw 能加入群聊，与其他 aiclaw 及人类用户在群内协作；同时将 aiclaw 的消息回复机制从"直接输出"升级为"思考过程 + 工具调用主动发言"，统一私聊与群聊的消息处理模式。

### 背景

当前 aiclaw 仅支持 1v1 私聊（owner / 好友）。REQ-002 和 REQ-003 均将"群聊"和"aiclaw 互通"列为延后项。现在需要让多个 aiclaw 在群内相互协作，这要求解决两个核心问题：

1. **消息路由**：群内消息如何分发给 aiclaw，aiclaw 如何决定是否回应
2. **无限循环**：两个 aiclaw 互相对话时如何避免消息风暴

### 核心思路

将 aiclaw 的消息回复从"直接输出消息到聊天窗口"改为"思考过程展示 + 调用 CLI 工具主动发言"：

- **之前**：收到消息 → AI 处理 → 流式回复直接作为聊天消息发出
- **之后**：收到消息 → AI 处理 → 思考内容流式展示（类似 think 过程）→ AI 自主决定是否调用 `aichat-cli send-message` 发送消息

### 本期范围

- aiclaw 加入群聊（主人建群、拉 aiclaw 入群）
- 群内消息上下文积累（无论是否回应）
- Think + Tool Call 消息机制（私聊 + 群聊统一）
- 思考内容落库（可查询审计）
- 群级配置：消息频率限制、是否需要 @ 触发
- aichat-cli 命令行工具开发
- MCP Server 封装（供未来非 openclaw agent 使用）

### 本期不做

- 自动建群 / aiclaw 自动拉群
- 跨群 aiclaw 协作
- 语音/图片等多模态群消息
- aiclaw 朋友圈互动

## 二、需求详述

### 2.1 群管理与 aiclaw 入群

**现有功能核实：**
- HuLa 应已有群管理审批机制（群主/管理员审批入群申请）
- aiclaw 入群由主人操作（主人是群主），主人将 aiclaw 拉入群
- 不需要 aiclaw 自己申请入群

**需核实项：**
- [ ] 确认 HuLa 现有群管理 API 支持群主拉人入群
- [ ] 确认 aiclaw（user_type=4）作为群成员的数据兼容性

### 2.2 群消息处理规则

**默认行为（可配置）：**
- aiclaw 收到群内所有消息，积累到自身会话上下文中
- 默认无限制：不需要 @ 即可触发回应
- 主人可在每个群中为自已的 aiclaw 配置规则

**群级配置项：**

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| 是否需要 @ | 否（所有消息可触发） | 开启后只有 @ 该 aiclaw 的消息才触发回应决策 |
| 频率限制（条/分钟） | 无限制 | 限制 aiclaw 在群内的发言频率，防刷屏 |
| 单次触发限制 | 仅人类用户 | aiclaw 发出的消息不触发其他 aiclaw 回应 |

**配置存储：** 新建表 `im_aiclaw_group_config`，主人可通过 aiclaw 管理页修改。

### 2.3 消息机制升级：Think + Tool Call（统一私聊与群聊）

#### 2.3.1 新模式消息流

```
发送者 → HuLa-Server → aichat-node → openclaw agent
                                        │
                                        ├─ 思考过程（thinking stream）
                                        │   → aichat-node → HuLa-Server
                                        │   → 前端展示为"思考中"状态
                                        │   → 落库（消息类型: thinking）
                                        │
                                        └─ 决策：是否需要回复？
                                            ├─ 需要 → 调用 hula_send_message Tool
                                            │   → aichat-node → HuLa-Server
                                            │   → 前端展示为正式聊天消息
                                            │   → 落库（消息类型: text）
                                            │
                                            └─ 不需要 → 结束
                                                （thinking 已落库，可查）
```

#### 2.3.2 统一私聊

私聊也采用此模式，理由：
- 消息机制统一，不需维护两套逻辑
- 更贴近人类沟通方式——不是每条消息都需要回复
- 用户可看到 aiclaw 的"思考过程"，理解为什么不回复

#### 2.3.3 思考内容落库

思考过程作为一种特殊消息类型持久化：

- 消息类型新增：`type = 5 (thinking)`
- 存储内容：思考的完整文本、处理时长、最终决策（是否发言及原因）
- 与普通消息关联：如后续调用了 `hula_send_message`，对应的聊天消息关联到该 thinking 记录
- 查询入口：聊天记录中可展开查看 thinking 内容；aiclaw 管理页可查看"未回复"的处理记录

### 2.4 防循环机制

**默认策略：** 无限制（主人信任自己的 aiclaw），由主人在群级配置中按需开启。

**配置项（每个群、每个 aiclaw 独立配置）：**

| 配置 | 默认 | 效果 |
|------|------|------|
| `mention_required` | false | true 时仅 @ 触发回应 |
| `rate_limit_per_minute` | 0（无限制） | >0 时限速 |
| `respond_to_ai` | false | true 时 aiclaw 也可被其他 aiclaw 的消息触发 |

**服务器端强制执行：** plugins/aichat-node 在调用 openclaw 前检查群配置，超出限制时跳过本轮处理，thinking 记录中标记 `skipped: rate_limited`。

### 2.5 aichat-cli 与 MCP

**aichat-cli 命令：**

```bash
# 发送消息到指定房间
aichat-cli send-message --room <roomId> --content "<text>"

# 发送消息到指定用户（私聊）
aichat-cli send-message --to <uid> --content "<text>"

# 查询群配置
aichat-cli group-config --room <roomId>
```

**实现方式：**
- `aichat-cli` 作为独立命令行工具，通过 HuLa-Server REST API 发送消息
- aichat-claw Plugin 将 CLI 注册为 openclaw Agent Tool（`hula_send_message` 等）
- 同时提供 MCP Server 封装，供未来非 openclaw agent 调用
- CLI 是核心原语，Tool 和 MCP 是两种调用传输层

## 三、协议变更

### 3.1 新增 WS 事件类型

**plugins → server（WSReqTypeEnum）：**

| 编号 | 名称 | 说明 |
|------|------|------|
| 20 | `THINKING_START` | aiclaw 开始思考 |
| 21 | `THINKING_DELTA` | 思考过程增量 |
| 22 | `THINKING_END` | 思考完成（含决策结论） |

**server → client（WSRespTypeEnum）：**

| 类型值 | dataClass | 说明 |
|--------|-----------|------|
| `"thinkingStart"` | ThinkingStartDTO | 思考开始 |
| `"thinkingDelta"` | ThinkingDeltaDTO | 思考增量 |
| `"thinkingEnd"` | ThinkingEndDTO | 思考结束 |

### 3.2 Thinking Payload 格式

```json
// THINKING_START (plugins → server)
{ "type": 20, "data": { "fromUid": 100001, "roomId": 300001, "triggerMsgId": "..." } }

// THINKING_DELTA (plugins → server)
{ "type": 21, "data": { "chunk": "正在分析...", "seq": 1 } }

// THINKING_END (plugins → server)
{ "type": 22, "data": { "fullContent": "完整思考内容...", "decision": "respond|skip", "reason": "..." } }
```

- `decision = respond`：将调用 `hula_send_message` 发送正式回复
- `decision = skip`：不发送消息，原因记录在 `reason` 中
- `decision = rate_limited`：被频率限制跳过

### 3.3 消息类型扩展

`im_message.type` 新增：
- `5` — THINKING（思考过程消息）

## 四、数据模型变更

### 4.1 新建 im_aiclaw_group_config 表

```sql
CREATE TABLE im_aiclaw_group_config (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    aiclaw_uid      BIGINT NOT NULL COMMENT 'aiclaw 用户 ID',
    room_id         BIGINT NOT NULL COMMENT '群房间 ID',
    mention_required TINYINT DEFAULT 0 COMMENT '是否需要 @ 触发',
    rate_limit_per_minute INT DEFAULT 0 COMMENT '每分钟发言限制，0=无限制',
    respond_to_ai   TINYINT DEFAULT 0 COMMENT '是否响应其他 aiclaw 的消息',
    create_time     DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    update_time     DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    UNIQUE KEY uk_aiclaw_room (aiclaw_uid, room_id)
);
```

### 4.2 im_message 扩展

- `type` 新增枚举值 `5` (THINKING)
- thinking 消息的 `content` 存储完整思考文本
- thinking 消息关联：当 `decision=respond` 时，后续发送的 text 消息的 `extra` 字段记录关联的 thinking msgId

## 五、前端规格（概要）

### 5.1 Thinking 展示

- 聊天窗口中以**临时状态条**展示"AI 助理正在思考..."
- 可展开/折叠查看完整思考过程
- 思考完成后状态条自动收起，保留在聊天记录中（可点击展开）
- 若 aiclaw 决定不回复，显示"已读，不回复" + 思考摘要

### 5.2 群级配置入口

- aiclaw 管理页 → 选择 aiclaw → "群聊设置"
- 列出该 aiclaw 所在的所有群
- 每个群可配置：@ 触发、频率限制、响应 AI

### 5.3 群聊 @ 检测

- 群聊输入框支持 @ 用户（包括 @ aiclaw）
- 被 @ 的 aiclaw 的 thinking 中会标注"被 @ 触发"

## 七、待 reviewer 确认的关键问题

1. **Think + Tool Call 统一私聊**：私聊从"直接回复"改为"think 后决定是否发言"，是否会影响现有用户体验？默认情况下 aiclaw 在私聊中是否总是选择回复？

2. **思考内容落库的粒度**：是否每次思考都完整落库？在高频场景下可能存在存储压力，是否需要保留策略（如 N 天后清理）？

3. **群配置的默认值**：默认无限制（不 @ 即可触发、不限频）是否合适？有无安全顾虑？

4. **MCP vs Tool 的优先级**：是否同意先实现 openclaw Tool，再封装 MCP Server？

5. **thinking 消息对现有消息查询的影响**：现有 `/api/chat/msg/list` 是否应默认过滤 thinking 类型，还是全部返回？

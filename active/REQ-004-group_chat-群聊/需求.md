## 一、概述

### 一句话
让 aiclaw 加入群聊参与协作；将消息机制从"直接回复"升级为"agent loop 思考 + MCP Tool 主动发言"，统一私聊与群聊。

### 核心思路

**之前**：收到消息 → AI 处理 → 流式回复直接作为聊天消息发出

**之后**：收到消息 → AI 进入 agent loop → 思考内容持续流式输出 → 在 loop 中自主决定是否调用 MCP Tool 发送消息（0 次、1 次或多次）→ loop 结束

### 关键变化

不再有显式的 "decision" 字段。agent 是否发言由它是否调用 MCP Tool 决定——调用了就有消息，没调用就没有。THINKING_END 仅表示本次处理循环结束。

## 二、需求详述

### 2.1 群管理与 aiclaw 入群

`RoomController.java:134` 已有 `POST /room/group/member` 邀请好友进群 API。

当被邀请 uid 属于邀请人的 aiclaw 时，系统自动同意入群（主人授权即通过）。

### 2.2 群消息处理

- aiclaw 收到群内所有消息，积累到自身会话上下文中
- 默认不需要 @ 即可触发 agent loop
- 上下文窗口：最近 N 条消息（默认 50），设计阶段细化

### 2.3 消息机制：Agent Loop 模型

#### 2.3.1 消息流

```
server → plugin → AI agent
                     │
          ┌──────────┴──────────┐
          │   agent loop        │
          │                     │
          │  持续输出 thinking   │──→ THINKING_START → DELTA... (流式)
          │   (推理/分析/决策)   │    → 前端：顶部可展开状态条，实时追加
          │                     │    → 落库：im_aiclaw_thinking
          │                     │
          │  调用 MCP Tool:     │
          │  hula_send_message  │──→ plugin → 直接发送完整消息
          │  (0次、1次或多次)   │    → 前端：正常消息气泡，一次性出现
          │                     │    → 落库：im_message (type=1 TEXT)
          │                     │
          │  loop 自然结束       │──→ THINKING_END
          │                     │    → 前端：思考条收起，保留回顾入口
          └─────────────────────┘
```

**关键点：**
- 思考和消息发送是**并行的**——thinking 过程中可能出现消息气泡
- 没有 decision 字段——agent 通过是否调用 Tool 决定发言
- THINKING_END 仅表示处理循环结束
- 思考内容**流式输出**（内容逐步生成）；MCP Tool 发送的消息**一次性投递**（内容已完整，无需 stream）

#### 2.3.2 私聊行为

私聊同样走 agent loop 模型。不做硬性"必须回复"约束——agent 自主决定。与群聊的区别仅在于上下文构建方式不同（私聊 1v1 上下文 vs 群聊多人上下文）。

#### 2.3.3 消息投递方式

- **thinking 内容**：流式投递（THINKING_START → DELTA → END），因为内容在 agent loop 中逐步生成
- **MCP Tool 发送的消息**：一次性投递完整消息，因为调用 Tool 时内容已经完整，无需用 stream 包装。走现有 WS 消息通道或 REST API 直接入库推送

#### 2.3.4 思考内容落库

使用独立表 `im_aiclaw_thinking`（详见 §4.2）：
- `content`：完整思考文本（TEXT 类型）
- `duration_ms`：处理耗时
- 关联 `trigger_msg_id` 和 `response_msg_id`（可多对多：一次 thinking 可能产生多条回复消息）

**过期策略**：
- 无回复消息的 thinking：保留 30 天
- 有回复消息的 thinking：保留 180 天
- XXL-Job 定时任务每日清理

### 2.4 防循环与限流

**规则（每个群、每个 aiclaw 独立配置，由主人修改）：**

| # | 规则 | 默认值 | 说明 |
|---|------|--------|------|
| 1 | 频率限制 | 10 条/分钟 | 设为 0 解除 |
| 2 | 每日总量上限 | 1000 条 | 安全兜底 |
| 3 | AI 互触发 | true | aiclaw 之间可互相触发对话 |
| 4 | 短回复跳过 | 最近 3 条回复均 < 10 字符时跳过 | 防止"好的""收到"类循环 |

**触发限制时**：aiclaw 自动回复一条消息说明原因（如"今日发言已达上限，暂停回复"），不计入限流统计。

**规则 1-3 由 aichat-node 在调用 agent 前检查，规则 4 在 agent 决定发送时检查。**

### 2.5 aichat-cli 与 MCP

**aichat-cli 命令：**

```bash
aichat-cli send-message --room <roomId> --content "<text>"
aichat-cli send-message --to <uid> --content "<text>"
aichat-cli group-config --room <roomId>
```

**认证**：使用 aiclaw token（`~/.aichat/credentials.jsonc`），Bearer 方式，权限范围仅限消息发送 + 配置查询。

**实现优先级**：openclaw Agent Tool 先行 → MCP Server 扩展（供非 openclaw agent）。

**消息发送路径**：agent 调用 `hula_send_message` Tool → aichat-claw Plugin → aichat-node → 直接发送完整消息到 HuLa-Server → 前端。aichat-cli 走 REST API，用于 agent 外部场景（如定时推送、外部事件触发）。

## 三、协议变更

### 3.1 WS 事件类型

**plugins → server（WSReqTypeEnum）：**

| 编号 | 名称 | 说明 |
|------|------|------|
| 20 | `THINKING_START` | agent loop 开始 |
| 21 | `THINKING_DELTA` | 思考过程增量 |
| 22 | `THINKING_END` | agent loop 结束（无 decision 字段） |

**server → client（WSRespTypeEnum）新增：**

| 类型值 | dataClass | 说明 |
|--------|-----------|------|
| `"thinkingStart"` | ThinkingStartDTO | 开始展示思考条 |
| `"thinkingDelta"` | ThinkingDeltaDTO | 追加思考内容 |
| `"thinkingEnd"` | ThinkingEndDTO | 思考条收起 |

**MCP Tool 发送的消息走现有消息通道（完整投递），不经过 STREAM 协议。现有 STREAM 协议（17/18/19）保留不动，供未来需要流式生成的场景使用。**

### 3.2 Thinking Payload

```json
// THINKING_START (20, plugins → server)
{ "type": 20, "data": { "fromUid": 100001, "roomId": 300001, "triggerMsgId": "..." } }

// THINKING_DELTA (21, plugins → server)
{ "type": 21, "data": { "chunk": "...", "seq": 1 } }

// THINKING_END (22, plugins → server)
// 无 decision 字段，仅表示 loop 结束
{ "type": 22, "data": { "durationMs": 3200 } }
```

### 3.3 im_message 不变

`im_message` 表结构和 `MessageTypeEnum` 不做任何变更。

## 四、数据模型

### 4.1 im_aiclaw_group_config

```sql
CREATE TABLE im_aiclaw_group_config (
    id                    BIGINT PRIMARY KEY AUTO_INCREMENT,
    aiclaw_uid            BIGINT NOT NULL,
    room_id               BIGINT NOT NULL,
    rate_limit_per_minute INT UNSIGNED DEFAULT 10 COMMENT '0=无限制',
    daily_limit           INT UNSIGNED DEFAULT 1000 COMMENT '每日上限',
    respond_to_ai         TINYINT UNSIGNED DEFAULT 1 COMMENT '是否响应其他 aiclaw',
    is_del                TINYINT UNSIGNED DEFAULT 0,
    create_time           DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    update_time           DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    UNIQUE KEY uk_aiclaw_room (aiclaw_uid, room_id)
);
```

### 4.2 im_aiclaw_thinking

```sql
CREATE TABLE im_aiclaw_thinking (
    id               BIGINT PRIMARY KEY AUTO_INCREMENT,
    aiclaw_uid       BIGINT NOT NULL,
    room_id          BIGINT NOT NULL,
    trigger_msg_id   BIGINT COMMENT '触发消息 ID',
    content          TEXT NOT NULL COMMENT '完整思考过程',
    duration_ms      INT COMMENT '耗时（毫秒）',
    create_time      DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    INDEX idx_aiclaw_room (aiclaw_uid, room_id),
    INDEX idx_trigger_msg (trigger_msg_id),
    INDEX idx_create_time (create_time)
);

-- thinking 与回复消息的关联（多对多）
CREATE TABLE im_aiclaw_thinking_msg_rel (
    thinking_id      BIGINT NOT NULL,
    msg_id           BIGINT NOT NULL COMMENT '关联的 im_message.id',
    PRIMARY KEY (thinking_id, msg_id)
);
```

### 4.3 im_message / MessageTypeEnum — 不变

## 五、前端规格（概要）

### 5.1 Thinking 展示

- 聊天窗口顶部显示**可展开状态条**："AI 助理 [name] 正在思考..."
- 状态条内实时流式追加思考内容
- agent 发送的正式消息正常出现在消息列表中（标准聊天气泡，流式输出）
- thinking 状态条与消息气泡**并行展示、互不阻塞**
- 同一群内多个 aiclaw 可能同时有 thinking 条（每个 aiclaw 一条）
- THINKING_END 后状态条收起，保留可回顾入口

### 5.2 群级配置入口

- aiclaw 管理页 → 选择 aiclaw → "群聊设置"
- 配置项：频率限制、每日上限、AI 互触发
- 修改后 Redis 缓存 + WS 通知实时生效

## 一、概述

### 一句话
让 aiclaw 能加入群聊，与其他 aiclaw 及人类用户在群内协作；同时将 aiclaw 的消息回复机制从"直接输出"升级为"思考过程展示 + 二次流式发言"，统一私聊与群聊的消息处理模式。

### 背景

当前 aiclaw 仅支持 1v1 私聊（owner / 好友）。REQ-002 和 REQ-003 均将"群聊"和"aiclaw 互通"列为延后项。现在需要让多个 aiclaw 在群内相互协作，这要求解决两个核心问题：

1. **消息路由**：群内消息如何分发给 aiclaw，aiclaw 如何决定是否回应
2. **无限循环**：两个 aiclaw 互相对话时如何避免消息风暴

### 核心思路

将 aiclaw 响应拆为两个阶段——**思考阶段**（流式展示思考过程）和**回复阶段**（复用现有 STREAM 协议流式输出正式回复）：

- **之前**：收到消息 → AI 处理 → 流式回复直接作为聊天消息发出
- **之后**：收到消息 → AI 处理 → **思考阶段**（THINKING_START/DELTA/END，流式展示思考过程）→ 决策 → 若需回复则进入**回复阶段**（复用现有 STREAM_START/DELTA/END 流式输出）→ STREAM_END 落库为正常消息

### 本期范围

- aiclaw 加入群聊（主人建群、拉 aiclaw 入群）
- 群内消息上下文积累（无论是否回应）
- 两阶段消息机制（思考 + 回复），私聊与群聊统一
- 思考内容落库到独立表（`im_aiclaw_thinking`），支持查询审计和过期清理
- 群级配置：@ 触发、频率限制、AI 互触发、对话深度检测
- 正式回复保持流式输出（复用现有 STREAM 协议，不退化）
- aichat-cli 命令行工具开发（含认证机制）
- MCP Server 封装（供未来非 openclaw agent 使用）

### 本期不做

- 自动建群 / aiclaw 自动拉群
- 跨群 aiclaw 协作
- 语音/图片等多模态群消息
- aiclaw 朋友圈互动

## 二、需求详述

### 2.1 群管理与 aiclaw 入群

**现有功能核实（2026-05-20）：**

`RoomController.java:134` 已有 `POST /room/group/member` 邀请好友进群 API：
```
POST /room/group/member  { roomId, uidList }
```

- 邀请人必须是群成员（`RoomAppServiceImpl.java:1057` 校验）
- 被邀请人收到邀请通知，需同意才能入群
- 群管理员收到邀请通知
- **适配 aiclaw 入群**：当被邀请 uid 属于邀请人的 aiclaw 时，系统自动同意入群（主人授权即通过），不需要 aiclaw 自己点击同意

**需核实项：**
- [x] 确认 HuLa 现有群管理 API 支持群主拉人入群 → 已确认，`POST /room/group/member`
- [x] 确认 aiclaw（user_type=4）作为群成员的数据兼容性 → 需 server-dev 在设计阶段验证 `GroupMember` 实体不限制 user_type

### 2.2 群消息处理规则

**默认行为（可配置）：**
- aiclaw 收到群内所有消息，积累到自身会话上下文中
- 默认不需要 @ 即可触发回应
- 频率限制默认 10 条/分钟（安全的默认值，owner 可调整或设为 0 解除限制）
- 主人可在每个群中为自已的 aiclaw 配置规则

**上下文窗口：** 群聊上下文取最近 N 条消息（N 可配置，默认 50），超过 token 限制时从最早的消息开始截断。详细策略在设计阶段由 plugin-dev 定义。

**群级配置项：**

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| 是否需要 @ | 否（所有消息可触发） | 开启后只有 @ 该 aiclaw 的消息才触发回应决策 |
| 频率限制（条/分钟） | 10 | 限制 aiclaw 在群内的发言频率，设为 0 解除限制 |
| 每日总量限制 | 500 | 安全兜底，即使 rate_limit=0 也生效 |
| 响应 AI 消息 | 否（默认不触发） | 开启后其他 aiclaw 的消息也可触发回应 |

**配置存储：** 新建表 `im_aiclaw_group_config`（详见 §4.1），主人可通过 aiclaw 管理页修改。修改后通过 Redis 缓存 + WS 通知 aichat-node 实时生效。

### 2.3 消息机制升级：两阶段（Think + Respond）

#### 2.3.1 新模式消息流

```
发送者 → HuLa-Server → aichat-node → openclaw agent
                                        │
                            ┌───────────┴───────────┐
                            │  阶段一：思考（Thinking） │
                            │  THINKING_START        │
                            │  → THINKING_DELTA(n)   │  ← 流式展示思考过程
                            │  → THINKING_END        │    落库 im_aiclaw_thinking
                            │    { decision, reason } │
                            └───────────┬───────────┘
                                        │
                        决策：是否需要回复？
                         ├─ skip → 结束
                         │    （私聊不可 skip，见 2.3.2）
                         │
                         ├─ rate_limited → 结束
                         │    （记录到 im_aiclaw_thinking）
                         │
                         └─ respond →
                             │
                 ┌───────────┴───────────┐
                 │  阶段二：回复（Respond）│
                 │  复用现有 STREAM 协议   │
                 │  STREAM_START          │
                 │  → STREAM_DELTA(n)     │  ← 流式输出正式回复
                 │  → STREAM_END          │    落库为正常消息（type=1 TEXT）
                 └───────────────────────┘
```

**关键设计决策：**
- **回复阶段复用现有 STREAM 协议**，保证正式回复仍是逐字流式输出，不退化
- THINKING 事件（20/21/22）**只承载思考阶段**，不混入聊天消息流
- 思考内容落库到独立表 `im_aiclaw_thinking`，不修改 `im_message` 表结构，不污染现有消息查询

#### 2.3.2 统一私聊（含行为约束）

私聊也采用两阶段模式，但有**硬性约束**：

| 约束 | 说明 |
|------|------|
| **私聊必须回复** | 私聊模式下 decision 不能为 skip。在 aichat-node 层面硬编码：若 decision=skip 且 room 为私聊，强制改为 respond |
| **system prompt 引导** | 私聊场景下注入"对用户的每条消息都必须回复"指令 |
| **回复保持流式** | 私聊回复也走 STREAM_START/DELTA/END，与现有体验一致 |

统一理由：
- 不维护两套代码路径，降低复杂度和 bug 概率
- 私聊中 thinking 展示是增值体验（用户看到 AI 思考过程），不是回复门槛

#### 2.3.3 思考内容落库（独立表）

**不入 im_message 表**（reviewer 建议 M2），原因：
1. `im_message.content` 为 `varchar(1024)`，思考内容通常 2000~10000 字
2. 思考记录与聊天消息生命周期不同（审计数据 vs 永久保留）
3. 避免污染现有消息查询 API、未读计数、消息统计

使用独立表 `im_aiclaw_thinking`（详见 §4.2）。

**过期策略**：
- `decision=skip` / `rate_limited`：保留 30 天
- `decision=respond`：保留 180 天（通过 `response_msg_id` 关联正式消息）
- 定时任务（XXL-Job）每日清理过期记录

### 2.4 防循环机制

**多层防护，依次生效：**

| 层级 | 机制 | 作用 |
|------|------|------|
| 1. 频率限制 | `rate_limit_per_minute`（默认 10） | 限制单个 aiclaw 发言频率 |
| 2. 每日上限 | `daily_limit`（默认 500） | 安全兜底，即使 rate_limit=0 也生效 |
| 3. AI 互触发 | `respond_to_ai`（默认 false） | 默认不响应其他 aiclaw 的消息 |
| 4. 对话深度检测 | 连续 aiclaw 回复链超过 3 轮强制中断 | 防止两个 respond_to_ai=true 的 aiclaw 交替循环 |
| 5. 近期 AI 占比检测 | 最近 10 条消息中 ≥70% 为 aiclaw 发出时跳过 | 防止 aiclaw 主导群聊 |

**第 4、5 层由 aichat-node 强制执行**，不依赖 owner 配置。

### 2.5 aichat-cli 与 MCP

**aichat-cli 命令：**

```bash
# 发送消息到指定房间（主动发言场景）
aichat-cli send-message --room <roomId> --content "<text>"

# 发送消息到指定用户（主动私聊场景）
aichat-cli send-message --to <uid> --content "<text>"

# 查询群配置
aichat-cli group-config --room <roomId>
```

**认证机制**（reviewer S5）：
- CLI 使用 aiclaw token 认证，存储在 `~/.aichat/credentials.jsonc`
- 调用 HuLa-Server REST API 时携带 `Authorization: Bearer <aiclawToken>`
- Token 权限范围：仅限消息发送 + 配置查询，不可执行用户管理、好友删除等操作
- server 端在 TokenContextFilter 中校验权限范围

**实现方式：**
- `aichat-cli` 是核心原语，通过 HuLa-Server REST API 发送消息
- aichat-claw Plugin 将 CLI 注册为 openclaw Agent Tool（`hula_send_message` 等）
- 同时提供 MCP Server 封装，供未来非 openclaw agent 调用
- 优先级：先 openclaw Tool，再 MCP Server

**注意：** 两阶段流程中的"回复阶段"不走 aichat-cli REST API，而是走现有 WS STREAM 协议（由 aichat-node 直接发起），保证流式输出。aichat-cli 用于 aiclaw **主动发言**场景（如定时推送、外部事件触发等）。

## 三、协议变更

### 3.1 WS 事件类型

**plugins → server（WSReqTypeEnum）：**

| 编号 | 名称 | 说明 | 与现有 STREAM 的关系 |
|------|------|------|---------------------|
| 20 | `THINKING_START` | aiclaw 开始思考 | 仅思考阶段，不生成消息 |
| 21 | `THINKING_DELTA` | 思考过程增量 | 仅思考阶段 |
| 22 | `THINKING_END` | 思考完成（含决策） | decision=respond 时触发后续 STREAM_START(17) |

**回复阶段复用现有 STREAM 协议（17/18/19），不变。**

**server → client（WSRespTypeEnum）新增：**

| 类型值 | dataClass | 说明 |
|--------|-----------|------|
| `"thinkingStart"` | ThinkingStartDTO | 思考开始，前端展示"思考中" |
| `"thinkingDelta"` | ThinkingDeltaDTO | 思考增量，前端追加内容 |
| `"thinkingEnd"` | ThinkingEndDTO | 思考结束，前端决定后续展示 |

### 3.2 Thinking Payload 格式

```json
// THINKING_START (20, plugins → server)
{ "type": 20, "data": { "fromUid": 100001, "roomId": 300001, "triggerMsgId": "..." } }

// THINKING_DELTA (21, plugins → server)
// 注：不携带 fromUid/roomId，server 通过 aiclawUid 关联活跃 thinking stream context 路由
{ "type": 21, "data": { "chunk": "正在分析用户意图...", "seq": 1 } }

// THINKING_END (22, plugins → server)
{ "type": 22, "data": {
    "fullContent": "完整思考内容...",
    "decision": "respond",
    "reason": "用户询问了 Python 相关问题，需要回答"
} }
```

**decision 取值：**
- `respond`：进入回复阶段，aichat-node 发起 STREAM_START(17)
- `skip`：不回复（仅群聊可用，私聊强制 respond）
- `rate_limited`：被频率/深度/占比限制跳过

### 3.3 消息类型 — 不变

`im_message` 表及 `MessageTypeEnum` **不做任何变更**。思考内容存储在独立表 `im_aiclaw_thinking` 中。

## 四、数据模型变更

### 4.1 新建 im_aiclaw_group_config 表

```sql
CREATE TABLE im_aiclaw_group_config (
    id                    BIGINT PRIMARY KEY AUTO_INCREMENT,
    aiclaw_uid            BIGINT NOT NULL COMMENT 'aiclaw 用户 ID',
    room_id               BIGINT NOT NULL COMMENT '群房间 ID',
    mention_required      TINYINT UNSIGNED DEFAULT 0 COMMENT '是否需要 @ 触发',
    rate_limit_per_minute INT UNSIGNED DEFAULT 10 COMMENT '每分钟发言限制，0=无限制',
    daily_limit           INT UNSIGNED DEFAULT 500 COMMENT '每日发言总量限制',
    respond_to_ai         TINYINT UNSIGNED DEFAULT 0 COMMENT '是否响应其他 aiclaw 的消息',
    is_del                TINYINT UNSIGNED DEFAULT 0 COMMENT '是否删除',
    create_time           DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    update_time           DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    UNIQUE KEY uk_aiclaw_room (aiclaw_uid, room_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### 4.2 新建 im_aiclaw_thinking 表

```sql
CREATE TABLE im_aiclaw_thinking (
    id               BIGINT PRIMARY KEY AUTO_INCREMENT,
    aiclaw_uid       BIGINT NOT NULL COMMENT 'aiclaw 用户 ID',
    room_id          BIGINT NOT NULL COMMENT '房间 ID',
    trigger_msg_id   BIGINT COMMENT '触发本次思考的消息 ID',
    content          TEXT NOT NULL COMMENT '完整思考内容',
    decision         VARCHAR(16) NOT NULL COMMENT 'respond|skip|rate_limited',
    reason           VARCHAR(512) COMMENT '决策原因',
    duration_ms      INT COMMENT '思考耗时（毫秒）',
    response_msg_id  BIGINT COMMENT 'decision=respond 时对应的正式消息 ID',
    create_time      DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    INDEX idx_aiclaw_room (aiclaw_uid, room_id),
    INDEX idx_trigger_msg (trigger_msg_id),
    INDEX idx_create_time (create_time),
    INDEX idx_response_msg (response_msg_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**设计要点：**
- `content` 使用 TEXT 类型，无长度限制
- 通过 `trigger_msg_id` 可追溯到触发消息
- 通过 `response_msg_id` 可关联到正式回复（im_message.id）
- 独立生命周期管理，到期定时清理，不影响 im_message 表
- 不在 im_message 表新增 type，现有查询逻辑零改动

### 4.3 im_message / MessageTypeEnum — 不变

`im_message` 表结构和 `MessageTypeEnum` **不做任何修改**。

## 五、前端规格（概要）

### 5.1 Thinking 展示

- 聊天窗口中以**临时状态条**展示"AI 助理正在思考..."
- 可展开/折叠查看实时思考过程（逐字追加，类似流式渲染）
- 若 decision=skip：显示"已读" + 思考摘要（可点击展开完整内容）
- 若 decision=respond：思考条收起，随后消息气泡以流式方式逐字出现（现有体验不变）
- 思考记录在聊天中保留为可展开项，点击可回顾

### 5.2 群级配置入口

- aiclaw 管理页 → 选择 aiclaw → "群聊设置"
- 列出该 aiclaw 所在的所有群
- 每个群可配置：@ 触发、频率限制、响应 AI

### 5.3 群聊 @ 检测

- 群聊输入框支持 @ 用户（包括 @ aiclaw）
- 被 @ 的 aiclaw 的 thinking 中会标注"被 @ 触发"
- 当 mention_required=true 且无人 @ 该 aiclaw 时，不触发思考
